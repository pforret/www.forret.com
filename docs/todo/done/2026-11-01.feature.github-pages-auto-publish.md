# Auto-publish site/ to GitHub Pages on git push

## Request
set up autio-publishing with Github upon git push

## Analysis
This is a new feature: nothing publishes the site yet. The workflow is already decided (see `CLAUDE.md`, Publishing): the HTML is built **locally** into `site/` and committed, and GitHub only serves it. There is no build in CI.

Current state, as checked on 2026-11-01:
- Remote: `git@github.com:pforret/www.forret.com.git` (public, default branch `main`), and `main` is in sync with `origin/main`.
- GitHub Pages is **not enabled** (`gh api repos/pforret/www.forret.com/pages` returns 404).
- No `.github/` folder.
- `site_url = "https://www.forret.test/"` in `zensical.toml` is still a local placeholder. The sitemap, RSS, social cards and canonical links depend on it.
- DNS (Gandi nameservers): `www.forret.com` is a CNAME to `redirect.toolstud.io.`, and `forret.com` points to `217.70.184.38`.

The key constraint: Pages' "deploy from branch" mode can only serve `/` (root) or `/docs`. `docs/` holds the Markdown sources, so a GitHub Actions workflow has to upload `site/` as-is.

## Impacted files
- `.github/workflows/pages.yml`: new; on push to `main` touching `site/**` (plus manual dispatch), it uploads `site/` and deploys it to Pages
- `zensical.toml`: `site_url` → `https://www.forret.com/`
- `CLAUDE.md`: Publishing section (push → Actions → Pages, the domain, the DNS step, mkdox2 build = commit + push = deploy)
- `site/`: regenerated after the `site_url` change

## Plan
See the PRP below.

## Acceptance criteria
- A push to `main` that changes `site/` triggers the workflow, and it finishes green.
- The published URL serves the same pages as the local `site/` (home, about, blog, `sitemap.xml`).
- `site_url` is `https://www.forret.com/`, and the links in `sitemap.xml` use it.
- No build step runs in CI; the deployed files are exactly the committed `site/`.
- `docs/todo/` content is not reachable on the published site.

## PRP

### Goal
Every `git push` to `main` that changes `site/` publishes that folder unchanged to GitHub Pages for the repo `pforret/www.forret.com`, with no build step on GitHub. The site works right away at `https://pforret.github.io/www.forret.com/`. After the user changes DNS at Gandi, it is served at `https://www.forret.com/` over HTTPS.

### Why
- Publishing becomes "build locally, push", which matches the workflow the user chose (`site/` is committed on purpose).
- `mkdox2 build` already commits and pushes, so a build is a publish.
- It replaces the current toolstud.io redirect on `www.forret.com` with the real personal site.

### Decisions taken
- Public URL → `www.forret.com` as a custom domain on Pages; `site_url = "https://www.forret.com/"` (user) (recorded: decisions/2026-11-01.publish-the-site-on-www-forret.md)
- DNS switch → the user changes the `www` CNAME at Gandi to `pforret.github.io.` **after** the deploy is shown to work; the agent does not touch DNS (user) (recorded: decisions/2026-11-01.user-switches-www-dns-at-gandi.md)
- Trigger → `push` to `main` with `paths: ['site/**']`, plus `workflow_dispatch` (user) (recorded: decisions/2026-11-01.deploy-github-pages-on-push-to.md)
- mkdox2 build always commits and pushes (broken `-z "$GITPUSH"` check) → accept it: build = publish. Document it, don't patch mkdox2 here (user) (recorded: decisions/2026-11-01.accept-that-mkdox2-build-commits-and.md)
- `docs/CNAME` file → not used. With Actions-based Pages, the custom domain is set in the Pages settings and a CNAME file in the artifact is ignored (default, from the GitHub docs)
- Setting the custom domain in the Pages settings → only after DNS points to GitHub. Setting it earlier makes `pforret.github.io/www.forret.com` redirect to `www.forret.com`, which still goes to toolstud.io, so the site would be unreachable (default)

### Known gotchas & guardrails
- Use these action versions (latest on 2026-11-01): `actions/checkout@v7`, `actions/configure-pages@v6`, `actions/upload-pages-artifact@v5`, `actions/deploy-pages@v5`. Pin them by major version.
- **No build step in the workflow.** No Python, no zensical, no docker. It uploads the committed `site/` and nothing else.
- Don't run `mkdox2 build` or `mkdox build` to regenerate: they `git commit` and `git push` on their own. Use `docker run --platform linux/amd64 --rm -v "$PWD":/docs pforret/mkdox-zensical build` instead.
- After changing `site_url`, rebuild, so `site/sitemap.xml` and the `feed_rss_*.xml` files carry `https://www.forret.com/`.
- Enabling Pages (`gh api ... /pages`) and pushing are outward-facing. Confirm with the user before each one; don't commit unless asked (fodo rule).
- Don't set `cname` in the Pages settings or touch DNS in this item (see Decisions). Leave the DNS step as instructions for the user.
- `zensical.toml` may be regenerated by mkdox2 upgrades. Keep the `exclude_docs` block (`/todo/`) when editing it.
- PRESERVE: `site/` stays committed. Don't add it to `.gitignore`.

### Approach
Add one workflow file, `.github/workflows/pages.yml`. It triggers on `push` to `main` with `paths: ['site/**']` and on `workflow_dispatch`, sets `permissions: contents: read, pages: write, id-token: write` and `concurrency: group: pages, cancel-in-progress: false`, and has a single deploy job in environment `github-pages`: checkout → configure-pages → upload-pages-artifact (`path: site`) → deploy-pages (`id: deployment`). Set `site_url` to `https://www.forret.com/` and rebuild `site/` with the plain docker command. Update the Publishing section of `CLAUDE.md` with the flow, the URL and the one-time DNS and custom-domain steps. Then, with the user's go-ahead: enable Pages with `build_type=workflow`, commit, push, and watch the run. Finally, hand the user the DNS instructions (Gandi: `www` CNAME → `pforret.github.io.`; afterwards `gh api -X PUT repos/pforret/www.forret.com/pages -f cname=www.forret.com` and enforce HTTPS).

### Validation loop (executable, in order)
```bash
# Level 1 — workflow syntax (actionlint if installed, otherwise YAML parse)
command -v actionlint >/dev/null && actionlint .github/workflows/pages.yml || python3 -c 'import yaml,sys;yaml.safe_load(open(".github/workflows/pages.yml"));print("yaml ok")'
grep -nE 'pip|zensical|docker|mkdocs' .github/workflows/pages.yml && echo "FAIL: build step in CI" || echo "ok: no build step"

# Level 2 — local build carries the right site_url and no todo content
docker run --platform linux/amd64 --rm -v "$PWD":/docs pforret/mkdox-zensical build   # expect "No issues found"
grep -c 'https://www.forret.com/' site/sitemap.xml        # expect > 0
grep -c 'forret.test' site/sitemap.xml site/feed_rss_*.xml # expect 0
test ! -e site/todo && echo "ok: no todo in site/"

# Level 3 — deploy (after user approval to enable Pages and push)
gh api repos/pforret/www.forret.com/pages --jq '.build_type'            # expect "workflow"
gh run list --workflow pages.yml --limit 1                               # expect a run for the pushed commit
gh run watch "$(gh run list --workflow pages.yml --limit 1 --json databaseId --jq '.[0].databaseId')" --exit-status
curl -sI https://pforret.github.io/www.forret.com/ | head -1            # expect HTTP/2 200
curl -s https://pforret.github.io/www.forret.com/sitemap.xml | grep -c www.forret.com   # expect > 0
curl -sI https://pforret.github.io/www.forret.com/todo/ | head -1       # expect 404
```

### Deviations from the spec
- The user had already enabled Pages and set the custom domain `www.forret.com` before the DNS switch (the PRP said to set the cname only after DNS). It was left as the user set it and resolved once DNS was switched. (recorded: decisions/2026-11-01.keep-the-pages-custom-domain-www.md)
- The user's GitHub-created `.github/workflows/static.yml` (deploy on every push) was deleted in favour of `pages.yml`, as the user chose. (recorded: decisions/2026-11-01.deploy-only-through-pages-yml-the.md)
- Unplanned fix: `.gitignore` contained `site/` (re-added by a mkdox2 regeneration), so new files under `site/` (CSS/JS bundles, fonts, portfolio, CV, timeline, posts) were never committed and the live site rendered unstyled with 404s. The `site/` line was removed and everything committed and pushed as `3073a46` (user approved). (recorded: decisions/2026-11-01.never-ignore-site-in-gitignore-because.md)

### Discoveries
- mkdox2 (template regeneration, commit `c8fa746`) writes `site/` into `.gitignore` and stopped tracking the theme JS bundle. With a committed-`site/` workflow, this silently publishes a broken site: already-tracked files keep updating, new ones are ignored.
- `mkdox2 build` commits and pushes (user commit `4583f0e`), so every build deploys, including a partial `site/` if `.gitignore` is wrong.
- Possible follow-up: a check in `pages.yml` that fails the deploy when key files are missing (e.g. `site/stylesheets/extra.css`, `site/assets/javascripts/bundle.*.js`).
- User task left: add `www.forret.com` in the Simple Analytics dashboard.
